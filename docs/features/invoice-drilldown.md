# Invoice Drill-Down (Budget-vs-Actual Actual column)

**Status:** Live (Phase 1 — read-only)
**RBAC:** `financials` area (admin / partner / business_dev). `field_ops` is BLOCKED
at both the `areaForPath` mapping and the handler's `requireArea` backstop.
**Branch:** `invoice-drilldown-datalayer-20260804`

## What it is

In the per-project **Budget vs Actual** table (project record, Financials section),
the office can now click an **Actual** cell that has invoices behind it. A modal
opens listing every invoice coded to that cost code — vendor, date, invoice number,
amount — each with an **Open PDF** link to the source document. A cost-code line with
no coded invoices shows an honest empty state (no fabricated rows). This turns the
single roll-up "Actual" number into an auditable, invoice-level drill-down.

## How a cell maps to its invoices — the ledger key

The drill-down is keyed **byte-identically** across three layers so a Budget-vs-Actual
row maps 1:1 to its invoices:

```
key = baNormTitle(groupTitle) + '|' + costCode
```

- `index.html` computes `baNormTitle(gtitle) + '|' + code` when it renders the
  clickable Actual cell (~line 12100) and when it builds the modal (~line 14069).
- `sync/build-invoice-ledger.py` uses `_norm_title()` — the same normalization — when
  it builds the ledger, so the keys always agree.

This is the exact key the portal already uses to overlay workbook actuals onto
Budget-vs-Actual rows, so the drill-down reuses the render loop's own key. The key
space does NOT collide with `project_budget_v1:` or `budget_actuals_refresh_request`.

## Data source

`platform/data/invoice-ledger.js` (`window.PF_INVOICE_LEDGER`) is the static feed,
generated by `platform/sync/build-invoice-ledger.py` from each project's **Turnover
Budget** workbook (col D Actual + col F vendor + col G notes) plus the SharePoint
`02 - Project Management/Expenses` PDFs. The client reads this feed directly to render
the clickable cells and the modal.

## API

`GET /api/invoice-ledger?job=<pf-number>` (`platform/functions/api/invoice-ledger.js`)

- Returns `{ ok, job, ledger: { "<normGroupTitle>|<costCode>": { invoices:[...], total } }, _meta }`.
- Gated to the `financials` area via `requireArea(session, 'financials')`; a
  `field_ops` session is denied even by direct URL.
- **Read order:** (1) KV `PF_SCHEDULE :: invoice_ledger_v1:<num>` — the future
  write-back store; (2) when KV is empty it returns an empty ledger with
  `source:'static-feed'` so the client falls back to `window.PF_INVOICE_LEDGER`.
- Fails **closed**: missing/unreadable session or wrong area -> denied, never allow.

The endpoint exists so a future write path can move the ledger into KV
(`invoice_ledger_v1:<num>`) with **zero client change**.

## How it is regenerated

Run `platform/sync/build-invoice-ledger.py` (excluded from deploy — lives under
`sync/`). It reads each project's Turnover Budget workbook + the Expenses PDFs and
rewrites `platform/data/invoice-ledger.js`. Current feed includes POET (26-002)
invoice 11320 and all backfill current as of 2026-08-04.
